# 文件域条目队列与授权契约

> 职责：定义一次写动作如何被解析成条目、条目如何入队合并撤回、授权发生在何处、review 如何呈现、提交包含什么。
> 依赖：[ACTIONS.md](ACTIONS.md)（动作集）、[VERSION.md](VERSION.md)（版本基准与锁）、[VIEW.md](VIEW.md)（条目字段）。
> 不回答：哈希算法细节与外部变更的分区判定（见 [VERSION.md](VERSION.md)）、动作自身的参数语义（见 [ACTIONS.md](ACTIONS.md)）。
> 状态：已实现（契约与实现一致）。

## 条目

队列的原子单元是**条目**，不是工具调用，也不是「一次编辑行为」。

每条条目由三元组表达：

```text
{ 操作, range_lines, 新内容 }
```

- `range_lines` 一律按 `H0` 的行号表达，是条目的唯一位置依据。
- 新内容为字面文本，不解析转义。
- 条目另记来源动作名（`source_action`），仅用于 review 标注与回执说明，不参与计算。

**一个范围或一处匹配即一条条目**。一次调用可能展开为多条：`replace_regex` 命中三处即三条，`delete_lines` 给多个 range 即多条。条目是最小内容单元；同一 hunk 内的条目会合并为一条 action，授权与撤回以 action 为单位。

## 归一

每个写动作在**入队时**解析为四种 lines 操作之一，此后队列只认这四种，不再认原始工具名：

| 原始动作 | 归一结果 |
| --- | --- |
| `append` | `append`：对末尾零宽度位置的插入 |
| `insert` | `insert`：对指定位置零宽度范围的插入 |
| `replace_lines` | `replace_lines`：替换给定 range |
| `replace_regex` | 按 `H0` 当场解析为确定 range，改写为 `replace_lines` 或 `delete_lines` |
| `delete_lines` | `delete_lines`：range 内容置空 |
| `create_file` | 对空文件的 `append` |
| `delete_file` | 覆盖全部行的 `delete_lines`，另在提交时移除文件本体 |

共同管理维度是 `range_lines`，因此**队列只有一种条目**，不存在「内容类」与「结构类」两套并行队列。

解析在入队时完成，预览与提交只使用已解析的 range，不再二次匹配。正则无匹配、行号越界在入队前即失败，不进入队列——因此已审阅的 range 不会因后续匹配结果变化而改变作用对象。

`create_dir`、`delete_dir` 不作用于文件内容、不产生 range，作为**结构条目**同级入队，以 `action` + `path` 表达，无 `range_lines`。

## 状态机

```text
        ┌──────────► rejected（撤下，不入队）
proposed┤
        └──────────► approved ──► withdrawn（撤回，重新合并）
```

- 条目提出后进入 `proposed`，不直接入队。
- `approved` 才算入队，可再撤回为 `withdrawn`。
- `rejected` 从视图撤下且不入队。
- 提交只纳入 `approved`；`proposed` 与 `rejected` 一律不提交。未审阅条目不会混进提交。

## 授权

人工授权**只发生在 review 一处**，且以 action（同一 hunk）为单位：

- 同一 hunk 内的多条 range 操作并成一条 action，只开一张票；批准或驳回一次即覆盖组内全部条目，**不允许对同一段改动拆开审批**。
- 不同 hunk 各自独立批准或驳回，**允许部分批准**——同一调用落在不同 hunk 的条目可分别处置。
- 同一调用被部分批准时，回执须区分已入队与被拒条目数，**不得宣称整次调用成功**。
- 不设批量批准、不设跳过 review 的开关。
- 提交前展示一次整队净 diff 供最终核对，该展示**只读**，不构成第二道审批。

写动作发起后先走前置校验（占用、权限、版本），**该链不含人工门**，因此允许先对某文件发起编辑、随后才看到 diff。

## 并 action

**并 action 属队列层**：已批准条目按 review 的并段规则合并——排序后两段之间未改动行不超过 6 行（或区间重叠）即并为**一条** action，`range_lines` 取并集，新内容按入队顺序由后者覆盖前者。合并阈值与展示层共用 `HUNK_MERGE_GAP`，因此 action 与 hunk 随同一规则切分，审批单元就是卡片上的整段改动。

- 合并**默认允许、不经用户批准**：由系统按 range 关系自动判定与执行，review 如实展示合并结果与覆盖次序。
- 合并后的 action 仍原子，可整体撤回；不支持对其中某一段单独撤回。因此合并只发生在语义上可接受同删的条目之间。
- 用户不同意合并结果时，只能驳回或整体撤回该 action，不提供拆分操作，也不设合并确认门。
- 合并只在 `approved` 集合内进行：被驳回的条目不参与合并，不产生覆盖争议。两条都批准且 range 重叠时，重叠部分以后入队者为准，并在 review 中标出被覆盖的条目。
- 撤回一条 action 只移除其 range 并重新合并，其余 action 语义不变。

**并 action 与展示层的并段共用一条规则**：两者都按 `HUNK_MERGE_GAP` 切分，队列的 action 因此与视图的 hunk 对齐，审批一次即覆盖卡片上的一整段。

## review 呈现

视图分两层，参考编辑器的变更列表：

**顶层——变更列表。** 文件与目录条目同级排列：

| 条目 | 标记 | 行数 |
| --- | --- | --- |
| 文件 | `A` / `M` / `D` | `+N −M` |
| 目录 | `A` / `D` | 不显示 |

`+N −M` 由该文件合并后的 `approved` 条目与 `H0` 比较得出。

**展开文件项——按行的连续 diff。** 最小展示单元是行，行内标注再给出所属 action 与原动作：

- 按行号升序连续呈现变更行与上下文行，每个变更行以**行内标注**给出所属 action 与原动作。
- 分段取 git 默认规则：改动行前后各 3 行上下文，两段之间未改动行 ≤ 6 时并段，超出即断为两个 hunk。
- 分段与队列的 action 合并共用 `HUNK_MERGE_GAP`：**hunk 与 action 对齐**，一段 hunk 就是一次审批与撤回的单位；同段内的多条 range 操作只出现一张票。
- 撤回入口挂在行内标注上，由该标注撤回其所属 action；列表层不重复提供条目级撤回。

**目录项无 diff**，只在列表中直接处置。

**零宽度 range**（插入点）不占实际字符位，渲染为 1 像素宽的装饰条（伪空格），新增浅绿、删除浅红，与列表的 `A` / `D` 同色；装饰条不计入行数与 `+N −M`。数据层用半开区间 `[n, n)` 表达，不引入独立 range 类型。

**面板非阻塞**：条目先入 `proposed`，面板实时刷新，模型可继续提出动作；只重算受影响的区间。

## 提交

- 提交时再次读盘并校验有效版本；不一致即拒绝提交，按 [VERSION.md](VERSION.md) 分区处置。
- 从 `H0` 起按已批准条目重算并写入，中间态不参与校验。
- 结构条目与 range 条目按入队顺序串行：`create_dir` 先于其下文件的 `create_file`；`delete_dir` 使其下未提交条目失效。
- 多文件提交不天然原子：逐文件报告成功、拒绝、冲突与失败，不宣称整体原子性。
- `delete_file` 在应用 range 后额外移除文件本体；仅有 `delete_lines` 权限时结果为空文件，文件仍存在。

## 非目标

- 不暂存文件全文或文件草稿；`H0` 只读副本不构成暂存内容。
- 不引入第二类队列、聚合审批入口或「一次性确认整批」的路径。
- 不在 review 中提供按 action 分组的折叠视图或视图切换。
- 不提供合并确认门与拆分已合并 action 的操作。
